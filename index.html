Qué contiene la fuente y qué proponemos

El JSON original de aeropuertos contiene códigos, nombres, ubicación y características de aeropuertos. No contiene vuelos ni rutas. Tampoco todos sus registros tienen servicio regular.

Derivado del JSON PAISES y AEROPUERTOS. Ampliación propuesta RUTAS y VUELOS; se poblarían con datos sintéticos, no extraídos.

Esta página documenta un diseño: no crea una base de datos ni genera vuelos automáticamente.

01. Diagrama entidad-relación

Diagrama lógico simplificado. Las etiquetas indican cuántas entidades de cada extremo pueden participar. Las dos relaciones de AEROPUERTOS con RUTAS tienen roles diferentes.

  • PAISES — AEROPUERTOS: un país tiene 0..N aeropuertos; un aeropuerto tiene 0..1 país conocido. La FK es opcional para admitir códigos ausentes en la fuente.
  • AEROPUERTOS — RUTAS (origen): un aeropuerto origina 0..N rutas; cada ruta tiene exactamente 1 origen.
  • AEROPUERTOS — RUTAS (destino): un aeropuerto recibe 0..N rutas; cada ruta tiene exactamente 1 destino.
  • RUTAS — VUELOS: una ruta tiene 0..N vuelos programados; cada vuelo pertenece exactamente a 1 ruta.

Una ruta resuelve una conexión dirigida entre aeropuertos. Un vuelo añade la ocurrencia temporal. No se deduce la existencia de ninguna de las dos a partir de que dos aeropuertos aparezcan en el JSON.

02. Modelo relacional

MODELO RELACIONAL

PAISES (codigo_pais)

AEROPUERTOS (id_aeropuerto, iata, icao, nombre, codigo_pais, continente_reportado, zona_horaria, desfase_utc_reportado, latitud, longitud, elevacion_pies, tipo, servicio_regular, wikipedia, web, longitud_pista_pies, flightradar24_url, radarbox_url, flightaware_url)

RUTAS (id_ruta, id_origen, id_destino)

VUELOS (id_vuelo, id_ruta, codigo_vuelo, salida_programada, llegada_programada)

Donde:

  • AEROPUERTOS.codigo_pais → PAISES.codigo_pais
  • RUTAS.id_origen → AEROPUERTOS.id_aeropuerto
  • RUTAS.id_destino → AEROPUERTOS.id_aeropuerto
  • VUELOS.id_ruta → RUTAS.id_ruta

03. Normalización: 1FN, 2FN y 3FN

La normalización depende de las reglas del dominio, no solo de añadir identificadores. Estas son las dependencias funcionales que asumimos para el diseño propuesto.

La revisión de 1FN, 2FN y 3FN corresponde al modelo lógico propuesto. Todavía no hemos creado físicamente las tablas ni sus restricciones. Al implementarlas habrá que definir las PK y FK, garantizar la unicidad de la pareja de origen y destino en RUTAS y validar los datos importados.

1FN · Valores atómicos

El diseño prevé un único valor por celda: un código, una coordenada o una fecha. No incluye listas de destinos ni columnas como vuelo_1 y vuelo_2. Cada relación tiene una PK definida para identificar sus futuras filas.

2FN · Dependencia completa

El modelo cumple 1FN y, bajo las dependencias asumidas, cada atributo no clave depende de una clave completa. Las PK son simples. Además, suponiendo única la pareja (id_origen, id_destino) en RUTAS, esta es una clave candidata que determina la ruta completa; no hay atributos descriptivos que dependan solo de un extremo.

3FN · Sin dependencias transitivas

Bajo las dependencias asumidas, el modelo cumple 2FN y no introduce dependencias transitivas entre atributos no clave. VUELOS incluye id_ruta, no sus aeropuertos; RUTAS incluye los identificadores de los aeropuertos, no sus nombres ni países. Esos datos se recuperarían con JOIN al implementar la base de datos.

Dependencias que justifican el modelo

  • id_aeropuerto → atributos del aeropuerto.
  • id_ruta → id_origen, id_destino; también (id_origen, id_destino) → id_ruta.
  • id_vuelo → id_ruta, codigo_vuelo, salida_programada, llegada_programada.
  • PAISES solo contiene su clave: no tiene atributos no clave que introduzcan dependencias transitivas.

Repetir un código de país o un tipo de aeropuerto no viola por sí mismo la 3FN. PAISES se separa para controlar la integridad referencial. Si añadimos su nombre, se almacenará allí, porque codigo_pais → nombre_pais, no en cada aeropuerto.

El continente se conserva como dato reportado por aeropuerto: no asumimos pais → continente. Tampoco asumimos zona_horaria → desfase_utc permanente: el desfase cambia con la fecha y el horario de verano. Para calcular horarios de vuelos se usarían la zona IANA y la fecha, no el desfase de la captura.

04. Buenas prácticas aplicadas al diseño

El modelo propuesto sigue estas buenas prácticas de diseño relacional:

  • Nombres de tablas en plural y campos con nombres claros y coherentes.
  • Claves primarias definidas para identificar cada registro y claves foráneas para relacionar las tablas.
  • Separación de países, aeropuertos, rutas y vuelos, evitando repetir datos descriptivos de otras entidades.
  • Distinción explícita entre los datos derivados del JSON y las rutas y vuelos propuestos para pruebas.

Estas prácticas complementan la normalización, pero no sustituyen la comprobación de 1FN, 2FN y 3FN. Su cumplimiento se refiere al diseño: al crear la base de datos habrá que implementar las PK, FK y restricciones, incluida la unicidad de la pareja de origen y destino en RUTAS, y validar los datos importados.
